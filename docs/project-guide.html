Database DB

ทุกอย่างเกี่ยวกับฐานข้อมูลอยู่ใน server/prisma/

server/prisma/schema.prismaDBหัวใจของฐานข้อมูล: กำหนดตาราง ฟิลด์ ความสัมพันธ์ และกฎห้ามซ้ำ
มีอะไรในไฟล์
  • enum 4 ตัว: Gender, PetSize, PetStatus (AVAILABLE/PENDING/ADOPTED), RequestStatus
  • model 5 ตัว: Species, Shelter, Pet, Adopter, AdoptionRequest
  • PK: ทุกตารางใช้ id Int @id @default(autoincrement())
  • FK: Pet.speciesId → Species, Pet.shelterId → Shelter, AdoptionRequest.adopterId → Adopter, AdoptionRequest.petId → Pet
  • @unique: Species.name, Species.slug, Shelter.name, Adopter.email
  • @@unique([adopterId, petId]): คนเดียวขอสัตว์ตัวเดิมได้ครั้งเดียว
  • onDelete: Restrict ห้ามลบ Species/Shelter ที่ยังมีสัตว์ผูกอยู่, Cascade ลบสัตว์แล้วคำขอของตัวนั้นหายตาม
  • @@index บน speciesId, shelterId, status เพื่อให้การกรองเร็วขึ้น
model AdoptionRequest {
  id        Int           @id @default(autoincrement())
  status    RequestStatus @default(PENDING)
  adopterId Int
  petId     Int
  adopter   Adopter @relation(fields: [adopterId], references: [id], onDelete: Cascade)
  pet       Pet     @relation(fields: [petId], references: [id], onDelete: Cascade)
  @@unique([adopterId, petId])
}
Prisma 7: ในไฟล์นี้ไม่มี URL ของฐานข้อมูล เพราะย้ายไปอยู่ใน prisma.config.ts แล้ว
server/prisma/migrations/DBไฟล์ SQL ที่ Prisma Migrate สร้างจาก schema.prisma (CREATE TABLE, FOREIGN KEY, UNIQUE INDEX)
  • 20261123002444_init/migration.sql คือ SQL จริงที่ใช้สร้างตารางทั้งหมดบน Supabase เปิดให้อาจารย์ดูได้ว่า @@unique กลายเป็น CREATE UNIQUE INDEX
  • ห้ามแก้ไฟล์ในนี้ด้วยมือ ถ้าเปลี่ยน schema ให้รัน npx prisma migrate dev --name ชื่อการเปลี่ยนแปลง Prisma จะสร้างโฟลเดอร์ใหม่ให้
  • migration_lock.toml บอกว่าใช้ provider postgresql
server/prisma/seed.tsDBสคริปต์ใส่ข้อมูลตั้งต้น 77 รายการ (สัตว์ 44, บ้านพักพิง 6, ผู้รับเลี้ยง 10, คำขอ 14, ชนิด 3)
ลำดับการทำงานใน main()
  1. ลบข้อมูลเดิม จากตารางลูกไปตารางแม่: AdoptionRequest → Adopter → Pet → Shelter → Species (ถ้าลบแม่ก่อนจะติด FK)
  2. สร้าง Species และ Shelter แล้วเก็บ id ไว้ใน Map/Array
  3. วนสร้าง Pet 44 ตัว โดยแปลง species: "dog" เป็น speciesId จริง ใส่รูปจาก placedog.net (สุนัข) และ cataas.com (แมว) ส่วนกระต่ายไม่มีรูป (หน้าเว็บแสดงอีโมจิแทน)
  4. ตั้ง createdAt ย้อนหลังกระจายกัน 0-43 วัน เพื่อให้เรียง "มาใหม่ล่าสุด" แล้วสุนัข แมว กระต่ายปนกัน
  5. สร้าง Adopter 10 คน และคำขอ 14 รายการ (อ้างอิงสัตว์ด้วยลำดับในอาร์เรย์ petData)

รันด้วย npx prisma db seed (ต้องอยู่ในโฟลเดอร์ server) รันซ้ำกี่ครั้งก็ได้ผลเหมือนเดิม แต่ id จะเริ่มนับต่อจากเดิม ไม่ได้เริ่มที่ 1 ใหม่

server/src/app.tsBEสร้าง Express app ใส่ middleware ตามลำดับ และ mount routes ทั้งหมดที่ /api
app.use(cors(allowedOrigins?.length ? { origin: allowedOrigins } : {}));  // อนุญาตให้ React (5173) เรียก
app.use(express.json({ limit: "100kb" }));  // แปลง JSON body เป็น req.body
app.use(requestLogger);                     // log: GET /api/pets 200 - 35ms
app.use("/api", apiRoutes);
app.use(notFound);      // เส้นทางที่ไม่มี → 404
app.use(errorHandler);  // ต้องอยู่ท้ายสุดเสมอ
ทำไม errorHandler ต้องอยู่ท้ายสุด: Express ส่ง error ไปยัง middleware ที่มี 4 parameter ตัวถัดไปตามลำดับที่ use ไว้ ถ้าวางไว้ก่อน routes จะไม่มี error มาถึง
server/src/lib/prisma.tsBEสร้าง PrismaClient ตัวเดียวใช้ทั้งโปรเจกต์ ผ่าน Driver Adapter ของ Prisma 7 (@prisma/adapter-pg)

ส่วนสำคัญ
  • petListInclude / petDetailInclude: บอก Prisma ให้ join species, shelter และนับจำนวนคำขอ (_count) มาด้วย Type ของผลลัพธ์ได้จาก Prisma.PetGetPayload อัตโนมัติ
  • buildWhere(query): แปลง ?speciesId=2&status=AVAILABLE&search=ส้ม เป็น where ของ Prisma ค้นหาแบบไม่สนตัวพิมพ์ใหญ่เล็กในชื่อ สายพันธุ์ และสี
  • listPets: ใช้ prisma.$transaction([findMany, count]) ได้ทั้งรายการและจำนวนรวมในครั้งเดียว ตอบ { data, meta: { total } }
  • getPet: ไม่เจอ → throw new HttpError(404, ...)
  • createPet ตอบ 201, deletePet ตอบ 204 (ไม่มี body)
  • replacePet (PUT) ใช้ schema เต็ม ส่วน updatePet (PATCH) ใช้ schema แบบ partial
ไม่ต้องเขียน try/catch: Express 5 ส่ง error จาก async function ไปที่ errorHandler ให้อัตโนมัติ เช่น update id ที่ไม่มี Prisma โยน P2025 แล้ว errorHandler แปลงเป็น 404
server/src/controllers/adoptionRequest.controller.tsBEคำขอรับเลี้ยง: สร้าง อนุมัติ/ปฏิเสธ ลบ และปรับสถานะสัตว์ให้ตรงกันใน Transaction
  • syncPetStatus(tx, petId): นับคำขอของสัตว์ตัวนั้น มีที่อนุมัติแล้ว → ADOPTED, มีที่รออยู่ → PENDING, ไม่มีเลย → AVAILABLE
  • createRequest: เช็กว่าสัตว์มีอยู่ (ไม่มี → 404) และยังไม่ได้บ้าน (ได้บ้านแล้ว → 409) จากนั้น upsert ผู้รับเลี้ยงด้วยอีเมล สร้างคำขอ และ sync สถานะ ทั้งหมดใน $transaction
  • ถ้าเจอ P2002 (ชน @@unique) ตอบ 409 "อีเมลนี้ได้ส่งคำขอรับเลี้ยงน้องตัวนี้ไปแล้ว"
  • updateRequestStatus: ถ้า APPROVED จะปฏิเสธคำขออื่นที่รออยู่ของสัตว์ตัวเดียวกันด้วย updateMany อัตโนมัติ
  • deleteRequest: ลบแล้ว sync สถานะสัตว์ใหม่
ทำไมต้องใช้ Transaction: หลายคำสั่งต้องสำเร็จพร้อมกัน ถ้าคำสั่งไหนพัง ทุกอย่างย้อนกลับ ข้อมูลจึงไม่ค้างครึ่ง ๆ กลาง ๆ เช่น สร้างคำขอแล้วแต่สถานะสัตว์ไม่เปลี่ยน

คำถามที่อาจารย์อาจถาม

กดเพื่อดูคำตอบสั้น ๆ ที่พูดได้ทันที

ทำไมต้องแยก Zustand กับ TanStack Query? ใช้ตัวเดียวไม่ได้หรือ
ข้อมูลสองแบบมีธรรมชาติต่างกัน ข้อมูลจาก Server ต้องจัดการ loading, error, cache, การโหลดใหม่ ซึ่ง TanStack Query ทำให้หมด ส่วน state ในเบราว์เซอร์ (ตัวกรอง ธีม รายการโปรด) ไม่ต้องยุ่งกับ Server เลย Zustand จึงง่ายกว่า ถ้าเอาข้อมูล DB ไปเก็บใน Zustand ด้วยจะมีสองที่ที่ต้องอัปเดตให้ตรงกัน เสี่ยง desync
Zero-Refresh ทำงานอย่างไร
ทุก useMutation มี onSuccess ที่เรียก queryClient.invalidateQueries({ queryKey: ["pets"] }) เพื่อบอกว่า cache ชุดนั้นเก่าแล้ว TanStack Query จะดึงข้อมูลใหม่ให้ query ที่กำลังแสดงอยู่ทันที หน้าจอจึงอัปเดตเองโดยไม่ต้องกด F5 (ดู features/pets/petApi.ts)
@@unique([adopterId, petId]) ใช้ทำอะไร ลองให้ดูได้ไหม
เป็นกฎในฐานข้อมูลว่าคู่ (ผู้รับเลี้ยง, สัตว์) ห้ามซ้ำ คนเดิมจึงขอสัตว์ตัวเดิมได้ครั้งเดียว Demo: ส่งคำขอด้วยอีเมลเดิมกับสัตว์ตัวเดิมสองครั้ง ครั้งที่สองได้ 409 "อีเมลนี้ได้ส่งคำขอรับเลี้ยงน้องตัวนี้ไปแล้ว" เพราะ PostgreSQL ปฏิเสธ (Prisma error P2002) แล้ว controller แปลงเป็น 409
PUT กับ PATCH ต่างกันอย่างไร
PUT ส่งข้อมูลครบทุกฟิลด์เพื่อแทนที่ทั้งหมด (ใช้ในฟอร์มแก้ไข ตรวจด้วย petCreateSchema) ส่วน PATCH ส่งเฉพาะฟิลด์ที่เปลี่ยน (ใช้ตอนเปลี่ยนสถานะในตาราง Admin ตรวจด้วย petPatchSchema ที่เป็น partial)
ทำไมลบสัตว์แล้วคำขอหายไปด้วย / ทำไมลบชนิดสัตว์ไม่ได้
ใน schema กำหนด onDelete: Cascade ที่ AdoptionRequest.pet ลบสัตว์แล้วคำขอของตัวนั้นถูกลบตาม ส่วน Pet.species ใช้ onDelete: Restrict ถ้ายังมีสัตว์ใช้ชนิดนั้นอยู่จะลบชนิดไม่ได้ ป้องกันข้อมูลกำพร้า
ถ้าส่งข้อมูลผิด Backend รู้ได้อย่างไร ทำไมไม่เชื่อหน้าเว็บ
คนอื่นยิง API ตรงได้โดยไม่ผ่านหน้าเว็บ (เช่น Postman) Backend จึงต้องตรวจเองทุกครั้งด้วย Zod (parseWith ใน controller) ถ้าไม่ผ่านตอบ 400 พร้อมรายละเอียดทุกฟิลด์ ส่วนการตรวจในฟอร์มฝั่ง client มีไว้ให้ผู้ใช้รู้เร็วขึ้นเท่านั้น
ทำไมใช้ Transaction ตอนส่งคำขอและอนุมัติ
การส่งคำขอมีหลายคำสั่ง: upsert ผู้รับเลี้ยง, สร้างคำขอ, เปลี่ยนสถานะสัตว์ ถ้าทำไม่ครบข้อมูลจะไม่ตรงกัน prisma.$transaction ทำให้สำเร็จทั้งหมดหรือย้อนกลับทั้งหมด
staleTime คืออะไร ตั้งไว้เท่าไร
ระยะเวลาที่ถือว่าข้อมูลใน cache ยังสด ไม่ต้องดึงใหม่ ตั้งไว้ 30 วินาที (lib/queryClient.ts) ส่วนชนิดสัตว์และบ้านพักพิงตั้ง 10 นาที เพราะแทบไม่เปลี่ยน แต่หลังเพิ่ม/แก้/ลบเรา invalidate เอง จึงไม่ต้องรอให้หมดเวลา
Type ของข้อมูลฝั่ง Backend มาจากไหน เขียนเองหรือ
ส่วนใหญ่ได้อัตโนมัติ: Type ของข้อมูลจาก DB มาจาก Prisma (Prisma.PetGetPayload) และ Type ของ body ที่ผ่านการตรวจมาจาก Zod (z.output) ฝั่ง client เราเขียน Type ใน types/models.ts ให้ตรงกับ schema
รายการโปรดจำได้อย่างไรเมื่อปิดเบราว์เซอร์
favoriteStore ใช้ middleware persist ของ Zustand บันทึกลง localStorage ที่ key matchapaw-favorites เปิด DevTools → Application → Local Storage ให้ดูได้ และเก็บแค่ id ไม่เก็บข้อมูลสัตว์
ถ้าฐานข้อมูลล่มหรือเน็ตหลุด หน้าเว็บจะเป็นอย่างไร
Backend ตอบ 503 (errorHandler จับ ECONNREFUSED) หรือถ้า Backend ไม่ได้เปิด apiClient โยน error "ไม่สามารถเชื่อมต่อเซิร์ฟเวอร์ได้" ทุกหน้าจะแสดง ErrorAlert พร้อมปุ่มลองใหม่ ไม่มีหน้าจอว่างหรือพัง
CORS คืออะไร ทำไมต้องใช้
หน้าเว็บ (localhost:5173) กับ API (localhost:3000) คนละ origin เบราว์เซอร์จะบล็อกการเรียกข้ามกัน ถ้า Server ไม่อนุญาต cors() ใน app.ts ใส่ header อนุญาตเฉพาะ origin ใน CLIENT_ORIGIN
